# USB networking on the original Bublcam

**Verified on one Bublcam (firmware 2.1.1) and one Windows 11 installation on 2026-09-24:** the camera works as a USB Ethernet/RNDIS gadget. Its USB hardware ID is `USB\VID_0525&PID_A4A2` and bus-reported description is `RNDIS/Ethernet Gadget`. Windows initially matched the USB class codes `02/02/FF` to Microsoft's `usbser.inf`, presenting a nonfunctional `USB Serial Device (COM4)`. The original driver was `usbser` version `10.0.26100.9278`; one passive COM4 open failed before any bytes were exchanged. This is an observation from this Windows setup, not a claim about all Windows releases or every Bublcam.

## Signed driver that worked

Windows' `netrndis.inf` is an internal template and did not offer an installable matching model via Device Manager's Have Disk dialog. The [Microsoft Update Catalog exact-ID result](https://www.catalog.update.microsoft.com/ScopedViewInline.aspx?updateid=38c84d13-eb1b-4327-aae5-e36e8cb7933d) supplies an older Acer-published, Microsoft WHCP-signed USB Ethernet/RNDIS Gadget package for AMD64/X86. Its `RNDIS.inf` explicitly maps `USB\VID_0525&PID_A4A2` in `[RndisDevices.NTamd64]` to `RNDIS.NT.5.1`, a Net-class `USB_RNDIS` driver using Windows' `usb8023.sys`. The INF reports version `1.0.0.0`, dated 2010-01-13. It is a legacy NDIS 5.1 package, not a modern NDIS 6.x driver. The [current Microsoft RNDIS template](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/remote-ndis-inf-template) explains why a device-specific INF is necessary.

The CAB was obtained directly from Microsoft's catalog and its Microsoft signature and extracted `rndis.cat` WHCP signature both validated. CAB SHA-256: `AEC19E7A9CADBC0B6C3369A71BEB3286C53363007C3FE209315D0D8B988574C7`; INF SHA-256: `D4BE3054B3D780D2DD7BED4CDC35824B324E7DF59A390A54A43F84DE1FB75666`. No signing security setting was changed. With the exact camera node present and healthy, an elevated `pnputil /add-driver RNDIS.inf /install` installed this signed package. On the tested machine Windows published it as `oem92.inf` (the published number varies by PC). It matched the exact hardware ID at rank `00FF0001`, outranking `usbser.inf`'s generic class match `00FF2004`. The device moved from Ports/COM4 to Net / `USB Ethernet/RNDIS Gadget`, service `USB_RNDIS`.

For the same fix on another PC: confirm the present camera's hardware ID and bus-reported description first; from the catalog entry above download the **Windows 7, Windows 8, Windows 8.1 and later** CAB (not the separate XP package), extract it with Windows' `expand -F:*` into a dedicated folder, and verify the extracted `RNDIS.inf` contains the exact ID under `[RndisDevices.NTamd64]` and that `rndis.cat` has a valid Microsoft WHCP signature. Then, from an elevated prompt, run `pnputil /add-driver <extracted-folder>\RNDIS.inf /install`. Check the resulting device's driver, class, service, and PnP status; reconnect the cable once if Windows loses the descriptor during the install reset. Do not select `netrndis.inf` directly or disable signature enforcement.

After the install, USB re-enumeration briefly failed with Windows' device-descriptor Code 43 placeholder `VID_0000&PID_0002`. Unplugging and reconnecting cable #3 once restored the real `0525:A4A2` device at PnP OK. Code 43 occurs before driver binding and should not be mistaken for evidence that the RNDIS package is incompatible; this camera/connection had shown the same intermittent descriptor failure earlier. If the actual `0525:A4A2` node is not present, do not configure or probe an unrelated interface.

## Live link and API

Windows created `Ethernet 3`, ifIndex 69 on this PC, link Up. It initially had only a self-assigned `169.254.x.x` IPv4 address and no USB route to `192.168.2.2`. Archived camera logs show Linux `g_ether`, `usb0` at `192.168.2.2`, and historical HTTP requests from `192.168.2.1` to the camera. After recording the adapter's prior DHCP/APIPA state, only the identified Bublcam adapter was assigned `192.168.2.1/24` in Windows' ActiveStore, with no gateway or DNS. `Find-NetRoute -RemoteIPAddress 192.168.2.2` then selected that USB adapter and the on-link `192.168.2.0/24` route. The address was still active at handoff; on this test, adding it disabled DHCP on that adapter. A future user should verify interface identity and route rather than copy `ifIndex 69` or `Ethernet 3` blindly.

Three pings to `192.168.2.2` replied with no loss and displayed times <=1 ms. Through that verified USB route, `GET http://192.168.2.2/osc/info` with `X-XSRF-Protected: 1` returned manufacturer `Bubl`, model `bubl1`, firmware `2.1.1`; `POST /osc/state` with `{}` and the same header also succeeded. The private response contains a device serial and is not published verbatim. USB therefore exposes the live Scarlet OSC HTTP service, not just charging.

A conservative TCP connect test found port 80 open. Ports 22, 23, 443, 554, and 8554 timed out while the camera was idle; timeout is **not** proof of closure. One later `_bublStream` command returned a dynamic RTSP endpoint on port 8554. `OPTIONS` and `DESCRIBE` to that path at `192.168.2.2` both returned RTSP 200. The stream was stopped, its command reached `done`, the test-owned session was closed, and `/osc/state` showed an empty session ID with no active stream. Actual RTP/H.264 frames were **not** captured or decoded over USB; `ffprobe`/`ffmpeg` were not available on this host.

## Recovery

Record the exact camera InstanceId and installed `oemNN.inf` before changing anything; `oem92.inf`, `Ethernet 3`, and ifIndex 69 are machine-specific examples. To restore the previous network settings while keeping RNDIS, remove only the `192.168.2.1/24` address from the identified USB adapter and re-enable its former DHCP setting. To return to automatic COM4 binding, first check whether any other device uses the same installed package or generic hardware ID, then uninstall only that published RNDIS package with administrator privileges (`pnputil /delete-driver oemNN.inf /uninstall`) and reconnect the Bublcam. The original `usbser.inf` is built into Windows and must **not** be deleted. Do not disable driver-signature enforcement or install drivers from third-party mirror sites.

The earlier controlled [USB PnP comparison](../research/usb-live-investigation-2026-09-24.md) records how the misleading COM4 binding and intermittent descriptor failure were identified; its pre-fix snapshots remain historically accurate.

A later [Wi-Fi/USB comparison attempt](../research/usb-wifi-comparison-2026-09-25.md) found intermittent USB RNDIS resets under subsequent traffic. The successful OSC/RTSP handshakes above prove capability at the time they occurred, not long-duration link stability. Do not assume USB is a reliable full-time replacement until that reset behavior is resolved.
